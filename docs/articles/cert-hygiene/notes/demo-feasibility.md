# Certificate Hygiene for Linkerd — Demo Feasibility

This plan converts the article’s failure modes into safe, disposable-cluster demonstrations. It does **not** prescribe production recovery. Each lab scenario must begin from a fresh local cluster and include an explicit restore step.

The likely result is **six high-confidence demonstrations**, **five proof-of-concept candidates**, and **four research-only cases**. The classifications are intentional: a faithful demo should reproduce an observable condition without pretending that an intermittent production incident has a deterministic cause.

## Safety and success rules

- Run only against a dedicated local `kind`/`k3d` cluster, never the developer’s current Kubernetes context.
- Create a baseline workload pair that proves meshed traffic, injection, and `linkerd check` are healthy before fault injection.
- Capture the baseline, the induced failure, the diagnostic evidence, and the post-recovery state for every scenario.
- Restore the original manifests/Secrets/configuration or tear down the disposable cluster. Do not demo key loss by destroying the only copy of a key outside the disposable cluster.
- Keep product-specific procedures grounded in [the bibliography](../sources.md); this plan records feasibility, not canonical operations.

## Article validation contract

The following is the required evidence set for the article’s principal certificate-expiry story. A scenario is not “replicated” merely because a certificate is past `notAfter`; it must capture the named observation from the disposable cluster, with exact product versions and timestamps.

| Article validation question | Demo scenario(s) | Required observation | Interpretation guardrail |
| --- | --- | --- | --- |
| **What happens immediately when the identity issuer expires?** | #5 | Record `notAfter` for issuer and affected workload certificates; sample `linkerd check --proxy`, identity-service logs, and a new identity request immediately before/after issuer expiry. | Do not claim that all mesh traffic fails at issuer expiry unless the lab shows it. The issuer’s expiry and a pre-existing workload leaf’s expiry are different events. |
| **How do existing workload certificates behave as they approach expiration?** | #5, #9 | Capture each workload certificate’s validity/refresh timestamp, current traffic, and renewal attempt at fixed intervals before leaf expiry. | “Approaching expiry” is a measurement window, not a single failure instant. Record the configured certificate lifetime and refresh behavior. |
| **What happens to newly started or restarted proxies after issuer expiry?** | #5 | Start a new meshed workload and restart a baseline workload after issuer expiry; capture init/startup result, identity logs, and readiness. | Compare against an untouched, already-running workload in the same cluster. This isolates issuance from ordinary traffic. |
| **Which exact proxy, log, and application errors are produced by failed identity renewal?** | #5, #9 | Preserve unedited proxy logs, `linkerd-identity` logs, application client/server error, and the command/operation used to create traffic. | Identify the failing connection and certificate chain; do not substitute a generic X.509 error from a different scenario. |
| **What is observable immediately after trust-anchor expiry?** | #6 | Timestamp root expiry; collect control-plane/proxy checks, new connection behavior, and identity-service logs immediately afterwards. | Treat this as emergency-recovery behavior, not planned root rotation. The lab result is version/configuration-specific. |
| **Do established connections survive, and for how long?** | #5, #6 | Keep a long-lived TCP/HTTP/2/gRPC stream and a periodic new-connection probe running across expiry; record start time, last successful exchange, and close/error time. | Never imply that TLS continuously revalidates a peer certificate. The demo must separately report established-session and newly negotiated-connection behavior. |
| **Which API-server errors are produced by each expired webhook certificate?** | #2 | Expire one webhook serving certificate at a time—proxy injector, policy validator, ServiceProfile validator, and Viz/tap when installed—then submit the matching API request and preserve the API-server error. | The affected API operation and `failurePolicy`/rules define blast radius; do not generalize one webhook’s error to every Kubernetes write. |
| **What exact `linkerd check` output appears for each failure?** | #1–#9, #13, #15 as applicable | Save raw `linkerd check` and `linkerd check --proxy` output before fault, during fault, and after recovery for every completed scenario. | Never paraphrase output in the article when the lab can provide a version-specific transcript. Label the Linkerd/Kubernetes version next to each transcript. |

### Timing-sensitive lab design

The issuer- and root-expiry scenarios are now mandatory proof-of-concept gates, not optional future work. The harness must be able to use short-lived, externally supplied lab credentials **or** another isolated, reversible means of moving only the Linkerd certificate clock. Altering the host or cluster clock is not acceptable until the harness proves that unrelated Kubernetes credentials and controllers are unaffected.

For every expiry scenario, run these probes concurrently:

1. A baseline `linkerd check` and `linkerd check --proxy` capture.
2. A continuous new-connection request between two meshed workloads.
3. A long-lived connection/stream between the same workloads.
4. A newly started workload and a restarted copy of an existing workload after issuer expiry.
5. Identity-service, proxy, Kubernetes API-server, and application log capture.

This turns the article’s questions into observations that can falsify an attractive but incorrect narrative—for example, that all traffic instantly fails at issuer expiry.

## Feasibility matrix

| # | Article failure mode | Classification | What a safe demo can show | Expected evidence | Recovery to demonstrate | Constraints / source basis |
| ---: | --- | --- | --- | --- | --- | --- |
| 1 | **Webhook serving certificate no longer chains to its configured CA bundle** | High confidence | Replace a webhook serving certificate with one signed by a different disposable CA, while preserving its configured `caBundle`. | Kubernetes API request fails calling the affected webhook; `linkerd check` reports the webhook TLS problem; already-running meshed traffic remains a separate concern. | Restore a matching certificate/CA bundle and confirm the affected API operation succeeds. | Kubernetes [Dynamic Admission Control](https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/) and Linkerd [webhook rotation](https://linkerd.io/2-edge/tasks/rotating_webhooks_certificates/) document this separate TLS relationship. |
| 2 | **Webhook certificate expired or invalid** | High confidence | Issue a deliberately short-lived disposable webhook serving certificate, wait for expiry, then exercise the matching admission/API path. | X.509 time-validity error from the API server/webhook path; `linkerd check` identifies the affected credential where applicable. | Regenerate/restore the webhook credential and matching bundle. | Demonstrates a webhook-only failure mode. The exact blast radius must be shown with the selected webhook’s `failurePolicy` and matching rules, not generalized. |
| 3 | **Webhook is unavailable even though the certificate is not the cause** | High confidence | Scale the selected webhook deployment to zero or block its service after recording valid certificate state. | Admission/API request fails with connection/refusal/timeout, while certificate inspection is healthy. | Restore replicas/connectivity and repeat the API operation. | A necessary negative-control demo for the triage table; see Kubernetes [admission-webhook good practices](https://kubernetes.io/docs/concepts/cluster-administration/admission-webhooks-good-practices/) and [Kubernetes #102013](https://github.com/kubernetes/kubernetes/issues/102013). |
| 4 | **Issuer certificate does not chain to the installed trust roots** | High confidence | Configure a disposable Linkerd installation with an issuer signed by CA B while its trust roots contain only CA A. | `linkerd check --proxy`/control-plane diagnostics identify an issuer/trust-root mismatch. | Restore an issuer signed by the trusted root, or use an intentionally prepared overlapping bundle as a planned-rotation variant. | Isolates chain mismatch from clock/expiry. Use Linkerd [troubleshooting](https://linkerd.io/docs/tasks/troubleshooting/) as the diagnostic authority. |
| 5 | **Issuer certificate is expired while the trust anchor and its key remain available** | Mandatory proof of concept | Install with a manually supplied issuer whose lifetime is short enough for a local wait, or use a controlled lab clock only if it does not invalidate unrelated cluster components. Run an untouched-workload probe, a new-connection probe, a long-lived stream, and a new/restarted workload probe across expiry. | Timestamped `linkerd check --proxy`, identity-service and proxy logs, application errors, workload-certificate metadata, and connection-lifetime results. | Replace the issuer under the same still-valid root, then verify control-plane/data-plane recovery. | The documented recovery branch is clear in [Replacing expired certificates](https://linkerd.io/docs/tasks/replacing_expired_certificates/); the POC is whether supported Linkerd versions accept sufficiently short issuer lifetimes for a practical demo. |
| 6 | **Trust anchor is expired** | Mandatory proof of concept | Start a disposable cluster with a short-lived root/issuer chain and let the root expire, or use a lab-only time shift after validating that it will not corrupt the cluster. Run the same new-connection and long-lived-stream probes. | Timestamped trust-root check failure, control-plane/proxy/application logs, and established-versus-new-connection results. | Follow the documented root-and-issuer replacement branch, including required restarts. | High instructional value but potentially slow and version-sensitive. Do not simulate by swapping one root in-place without preserving the recovery framing. |
| 7 | **Planned trust-anchor rotation with overlap** | High confidence | Use two disposable CAs: establish baseline on old root, distribute an old+new trust bundle, move the issuer to the new root, restart/roll workloads as required, then remove the old root. | Every intermediate state has a verifiable trust bundle and successful traffic/checks. | The scenario itself is the recovery-free result; include a teardown to remove the old root. | This is a planned-maintenance demo, not a failure demo. It is the positive control for why a hard root replacement is risky. Source: Linkerd [automatic control-plane TLS rotation](https://linkerd.io/2-edge/tasks/automatically-rotating-control-plane-tls-credentials/). |
| 8 | **Hard root replacement without a bundle transition** | High confidence | In the same disposable lab, replace the trusted root/issuer in one step rather than using the overlap path. | Old proxies/workloads cannot validate identities across the old/new trust boundary; checks reveal mismatched trust configuration. | Tear down and rebuild the baseline, then repeat as the staged-rotation scenario. | This is intentionally destructive only to the disposable cluster. It demonstrates why the staged procedure exists; do not label it “the most common” outage. |
| 9 | **Identity service/control plane unavailable during proxy certificate renewal** | Proof of concept | Use short-lived workload identities if supported, then block proxy access to the identity service for longer than the renewal interval. | Identity acquisition/refresh errors; only after credentials expire should traffic be expected to fail. | Restore identity-service reachability; restart only the affected workload if the tested version cannot recover automatically. | The failure is reported in [Linkerd #13136](https://github.com/linkerd/linkerd2/issues/13136). A practical demonstration depends on configurable/testable leaf lifetime and refresh interval. |
| 10 | **Issuer Secret changed but a running component keeps an old issuer** | Research-only | No deterministic fault injection is currently known. A Secret update can be observed, but deliberately reproducing a missed mounted-Secret refresh would risk inventing a cause. | If it occurs, compare Secret resource version, mounted content, identity logs, and certificate `NotAfter`. | Follow version-supported reload/restart recovery only after evidence establishes the stale consumer. | [Linkerd #15109](https://github.com/linkerd/linkerd2/issues/15109) was closed without a deterministic reproduction or confirmed root cause. |
| 11 | **Trust bundle update is not consumed until components restart** | Proof of concept | Update a disposable trust bundle, then compare new pods with existing pods before/after intentional rollouts. | Old and new process generations report/use different trust state. | Roll the documented control-plane and workload components, then verify convergence. | Reported in [Linkerd #13613](https://github.com/linkerd/linkerd2/issues/13613). This must be tested against the selected Linkerd version, not assumed. |
| 12 | **GitOps reconciler overwrites generated webhook TLS material** | Research-only unless GitOps is in scope | A local GitOps controller could be configured to continuously reapply stale Secret/webhook state. | Fresh install passes; later webhook check fails after reconciliation. | Configure explicit ownership/ignore rules or use externally managed credentials. | [Linkerd #13361](https://github.com/linkerd/linkerd2/issues/13361) provides a resolved real-world example. It adds an entire GitOps product to the demo and should be separate from the core lab. |
| 13 | **cert-manager issuer cannot initialize from supplied Secret** | High confidence | Apply a deliberately malformed or incomplete disposable issuer Secret/reference. | cert-manager events/logs identify the missing/wrong data; Linkerd install cannot proceed. | Apply a correctly shaped Secret and wait for issuer readiness before installing Linkerd. | Based on [Linkerd #11972](https://github.com/linkerd/linkerd2/issues/11972). A good setup-validation scenario rather than a running-mesh outage. |
| 14 | **Renewal status appears healthy while the deployed certificate is unusable/expired** | Proof of concept | Use a deliberately stalled cert-manager issuance path and compare resource condition, `notAfter`, and endpoint/Secret inspection. | Divergence between convenience status and actual certificate validity/deployment state. | Repair the issuance dependency and verify the renewed certificate is both issued and consumed. | [cert-manager #7895](https://github.com/cert-manager/cert-manager/issues/7895) is an open report; keep the demo’s assertion narrow to the tested version/configuration. |
| 15 | **Time-valid certificate becomes unacceptable due to algorithm policy** | High confidence | Configure a disposable webhook chain using an algorithm rejected by the selected Kubernetes/Go version, then call the webhook. | X.509/algorithm-policy validation failure rather than `notAfter` expiry. | Replace the chain with supported cryptography. | A valuable triage negative control based on [Kubernetes #110530](https://github.com/kubernetes/kubernetes/issues/110530): certificate errors are not synonymous with expiry. |

## Recommended demo sequence

Build the smallest reliable lab first. It should show the two trust relationships separately and should finish in minutes, excluding intentionally short certificate lifetimes.

1. **Baseline:** disposable cluster, Linkerd, and two meshed test workloads; record successful traffic and `linkerd check`.
2. **Webhook triad:** mismatch (#1), expired/invalid serving certificate (#2), and unavailable webhook (#3). These establish the admission path and its look-alikes.
3. **Mesh identity chain:** issuer/root mismatch (#4), then planned root rotation (#7) and hard replacement (#8). These establish why a trust bundle transition matters.
4. **Setup/automation:** malformed external issuer material (#13), then only attempt #5, #9, #11, and #14 after proving their version-specific prerequisites.
5. **Research-only appendix:** document #10 and #12 as real operational reports that a deterministic demo should not claim to recreate.

## Acceptance criteria for a scenario

Each completed scenario should include a short runbook with:

- **Initial state:** exact Linkerd, Kubernetes, and cert-manager versions; manifests and certificate metadata (serial, issuer, SANs, `notBefore`, `notAfter`).
- **Fault action:** one reversible mutation in the disposable cluster.
- **Observed symptom:** the operator-visible error, affected operation, and what still works.
- **Diagnosis:** `linkerd check` output plus direct certificate/bundle inspection; do not infer expiry from an error string alone.
- **Recovery:** the least disruptive valid repair for this exact induced state.
- **Verification:** successful checks, recovered operation, and cleanup/cluster teardown.

## First implementation decision

Start with scenarios **#1, #2, #3, #4, #7, #8, and #13**, then immediately prove the short-lived-credential prerequisites for mandatory scenarios **#5** and **#6**. The first group establishes both certificate landscapes; #5 and #6 supply the article’s central expiry evidence and cannot be replaced with generic or historical errors.
