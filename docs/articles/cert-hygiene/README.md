# Certificate hygiene for Linkerd — article materials

Research and lab results for an article on recognising, fixing and preventing certificate-expiry problems in Linkerd.

## Status

Every experiment below has been run, written up, and carried into [findings.md](findings.md) and [sources.md](sources.md). Its triage table no longer has an untested half — and, since the two negative controls in the last bullet, it no longer rests entirely on expiries either: three of its causes have now been produced in the lab, one of them a webhook whose certificate was perfectly healthy and one a certificate that was time-valid and refused anyway.

- **Identity issuer expiry:** run three times (once, then twice more with fuller recording). Reproduced. The repeats also settled how the handshake fails, which restarts recovery needs, and how long an already-open connection lasted.
- **Webhook serving certificates:** run twice, once per failure policy. Reproduced — with the important qualification that two of the three webhooks kept working past their own expiry, about 30 minutes for the proxy injector and about 10 minutes for the ServiceProfile validator, until the API server had to reconnect.
- **Identity-service outage:** run once. Reproduced, including the answer to whether a proxy re-certifies on its own afterwards (it did not). One thing that run saw but cannot explain is recorded as an open question.
- **Trust-anchor expiry:** run once. Reproduced, except that failures did not stagger across proxies as expected; whether recovery needs the identity service restarted separately is unresolved.
- **Trust-anchor rotation:** run twice, staged and one-step. Reproduced; the guidance in the findings is rewritten from it.
- **The `linkerd check` 60-day warning:** run ten times — twice in the second round, then eight more as a bisect; nine of the ten are valid evidence, the tenth having been recorded against a dirty tree. Reproduced in both directions, and the boundary is now measured rather than bracketed by a day: it is not at 60 days. The check still printed that `‼` warning with 58 m 58 s *more* than 60 days of validity remaining, and cleared to `√` only once an issuer had 1 h 4 m 3 s more — so the row is still warning almost an hour's worth of validity past the 60-day mark, and therefore at exactly 60 days too; the warning starts roughly an hour before that mark is reached, not when it arrives. [findings.md](findings.md) now quotes that 305-second bracket rather than a single figure, and records why the check wants the extra margin as still open. The runs also settled something sharper: the warning never fails the command. Every transcript the experiment recorded exits 0, `‼` issuer row and all, including checks against an issuer 14 m 38 s from expiry — so anything monitoring `linkerd check` by its exit code never sees it, and the pages say so where they advise how to watch for expiry.
- **Viz/tap API certificate expiry:** run once. Reproduced, with the same qualification the webhook experiment found: `linkerd viz check` went fatal at the first observation after expiry, but the tap APIService stayed available and `linkerd viz tap` kept returning live events for about half an hour afterwards, until a restart of the tap pod forced the API server to open a new connection. Its triage row is now in [findings.md](findings.md)'s triage table, carrying that distinction, together with the masking effect the fatal row has on the rest of `linkerd viz check`. The remaining scenarios in [notes/demo-feasibility.md](notes/demo-feasibility.md) still rest on Linkerd's source code only.
- **Two failures that are not expiry — the negative controls:** a webhook scaled to zero with a perfectly healthy certificate, run twice (once per failure policy), and a certificate that is time-valid and correctly chained but signed with SHA-1, run once. Both written up in [notes/lab-evidence-not-expiry.md](notes/lab-evidence-not-expiry.md). The unavailable-webhook scenario counts as reproduced — every acceptance condition holds. The refused-certificate scenario is **not** called reproduced without a qualifier: one of its acceptance conditions asks for the refused certificate's `notAfter` at every tick, which cannot be met as written, because that certificate was installed at five of the run's 27 ticks; the note says how the implementation reads it and why that reading is at least as strong. Two results change what the triage table has to do. First, under `failurePolicy=Ignore` an *unavailable* injector and an *expired* injector certificate produce the same admitted pod — the two recorded objects differ only in the object's identity and six timestamps — so the symptom "pods have no proxy" does not identify the cause; what separates them is the API server's error text and whether the webhook's pods are running. Second, the prediction that `linkerd check` would call a refused certificate valid was **wrong**: the row went fatal at the first observation and named the algorithm, so the lab's "the check is green while things are broken" finding does not extend to that cause. Both experiments also show, again, that `linkerd check` halts at the first failing section — the certificate section was never reached at all in the unavailable-webhook runs — so a row's absence is not a pass and a green row only means the check got that far. Both are now carried into [findings.md](findings.md), whose triage table gained a "how to tell it from the look-alikes" column, two new rows and a side-by-side comparison of the three causes, and into [sources.md](sources.md), which has an entry per experiment with the over-readings each one forbids. One existing page claim was qualified rather than deleted in the process: "`linkerd check` can be green while things are broken" is true for the causes it was drawn from and false for the refused certificate, and the pages now say which is which.

## The test lab

The experiments run in [`demos/cert-hygiene/`](../../../demos/cert-hygiene/): a throwaway single-machine Kubernetes cluster with Linkerd. It breaks a credential or a component on purpose — usually by making a certificate expire, and twice by making sure nothing did — and records everything that happens. Raw recordings of each run are kept outside this repository, so that cloning it stays cheap for anyone who just wants to run the demos. What stays here is a manifest per run listing every file with its checksum; `tools/evidence.sh` prints any single recorded file, or downloads a whole run and verifies it against that manifest.

How the lab works is in its [first design](../../superpowers/specs/2026-09-10-cert-hygiene-demo-lab-design.md) and [first implementation plan](../../superpowers/plans/2026-09-10-cert-hygiene-demo-lab/README.md). The second round of experiments — every scenario, credential profile, restart stage and validity rule behind the evidence on these pages — is specified in its [second design](../../superpowers/specs/2026-09-11-cert-hygiene-lab-slice-2-design.md) and [second implementation plan](../../superpowers/plans/2026-09-11-cert-hygiene-lab-slice-2/README.md). All four use internal shorthand that the pages above avoid.

## Research conventions

- Treat current Linkerd documentation as the source of truth for Linkerd behavior and operational procedures.
- Use Kubernetes, IETF, NIST, and cert-manager material to support underlying mechanics and general operational guidance.
- Treat GitHub issues and discussions as historical examples, not as current runbooks or universal behavior.
- Before adding article copy, map factual claims to [sources.md](sources.md) and keep any qualifications it records.
