RetailCloud
How this demo works
DashboardTutorial

RetailCloud is a cloud dashboard reading live data from a store’s point-of-sale system that runs on a different machine, outside Kubernetes. Here’s how they trust each other — by identity, not by network.

The problem

Trust across a boundary

The dashboard runs in the cloud (machine A). The point-of-sale system runs on-prem in the store (machine B). When the dashboard asks the store for inventory, how does the store know the caller is really the dashboard — and not something else that reached its address? Firewalls and IP allowlists tie trust to where a workload runs. Move it, or share a network, and those rules break.

The idea

SPIFFE: identity, not location

SPIFFE gives every workload a cryptographic identity — a short-lived certificate called an SVID — inside a shared trust domain. The store’s service isn’t “whatever is at 100.77.68.7”; it is:

spiffe://root.linkerd.cluster.local/store-pos

That identity is the same regardless of what network the workload sits on.

The bridge

Mesh expansion: the store joins the mesh

store-pos runs on a plain VM, not in Kubernetes. Linkerd’s mesh expansion brings it in: a standalone linkerd2-proxy runs beside it, and SPIRE issues its SVID — chained to the same trust anchor Linkerd uses inside the cluster. One trust domain now spans both machines.

The wire

mTLS: encrypted and mutually authenticated

When the dashboard calls the store, both sides present their SVIDs and establish mutual TLS. The store knows exactly who is calling — by identity — and the traffic is encrypted the whole way across the boundary. On the dashboard you’ll see the link marked mTLS with live latency.

The point

Authorization by identity

Access becomes a policy about identity: the store-pos service allows only the dashboard’s identity to read its data. Change the allowed identity, and the dashboard is refused — a real HTTP 403 — with nothing about the network changing. That’s exactly what the dashboard’s Void authorization button does. Reproduce it on two Linux hosts (or VMs) that can reach each other. This is the shape; the exact scripts are in the repo.

Prerequisites

What you need

  1. Two Linux hosts on any network where they can reach each other (LAN, VPN, or an overlay).
  2. Linkerd 2.15+ (mesh expansion + SPIFFE), a Kubernetes cluster (k3s is fine), and SPIRE.
Step 1

One trust anchor

Generate a root CA and install Linkerd with it — this root is the shared trust domain both machines will chain to.

# on the cluster host
step certificate create root.linkerd.cluster.local ca.crt ca.key \
  --profile root-ca --no-password --insecure
linkerd install --identity-trust-anchors-file ca.crt \
  --identity-issuer-certificate-file issuer.crt \
  --identity-issuer-key-file issuer.key | kubectl apply -f -
Step 2

The store joins the mesh

On the store host, run SPIRE rooted at that same anchor, register the workload’s identity, and run a standalone proxy beside store-pos.

# on the store host — SPIRE server+agent use the copied ca.crt/ca.key
spire-server entry create \
  -parentID spiffe://root.linkerd.cluster.local/agent \
  -spiffeID spiffe://root.linkerd.cluster.local/store-pos \
  -selector unix:uid:0
# extract + run linkerd2-proxy (identity from SPIRE), set up iptables, run store-pos
Step 3

Register + authorize

Tell the cluster about the external workload, then allow only the cloud app’s identity to reach it.

# ExternalWorkload + a Server + AuthorizationPolicy
kind: MeshTLSAuthentication
spec:
  identities:
    - retail-cloud.mixed-env.serviceaccount.identity.linkerd.cluster.local

Change that identity and the dashboard gets a 403 — the “Void” button patches exactly this.
